# Spark session optimization for yarn mode

We have seen how to optimize a spark session in local mode, in this tutorial, we will learn how to optimize a spark session in yarn mode.

## 1. Basic concept of a spark job

A spark job in yarn cluster has two parts:
- driver
- worker/executor

The `Spark Driver` acts as the brain and coordinator, while `Spark Executors` act as the muscle performing parallel computations.

### 1.1 The spark driver

In a yarn cluster, the spark driver role is
- Converts Code to DAG / Task Stages
- Requests Containers from YARN RM
- Schedules Tasks to Executor Slots
- Collects Results / Action Data


The locality of spark driver is quite different based on `YARN Deploy Modes`:

- `client Mode`: Driver runs on the client machine where the spark job was launched (not the cluster). 
               `If the client disconnects or network drops, the application dies.` (e.g. pyspark in notebook, sparklyr in Rstudio)
- `cluster Mode`: Driver runs inside a `YARN ApplicationMaster` container managed by YARN on one of the cluster worker nodes. 
                  Essential for long-running batch jobs in production. (e.g. spark-submit)

### 1.2 The spark worker/executor 

A spark worker is referred to a server(e.g. physical or VM) in a spark cluster. A `spark executor` is referred to a 
container(jvm process) which can run tasks of a spark applications. So a spark worker may have multiple executors in it.

It has 4 main functions:

- `Task Execution`
- `In-Memory Caching & Storage`
- `Shuffle Data Management`
- `Heartbeating`

## 2. Spark Job Optimization

There are two main part of a spark job configuration

- Calculation parallelism
- Memory management for data storage

### 2.1 Calculation parallelism

The calculation parallelism depends on two factors:

- Total Concurrent Task Slots
- data partition number


#### 2.1.1 Data partition

Base on the which file system you use, the data partition size varies.

For example, if we use HDFS, the default block size is 128MB, for a file of 1GB, we will have roughly 8 partitions.

> 8 partitions means this spark job can be divided into 8 sub-tasks at most.

#### 2.1.2 Total Concurrent Task Slots

The Total Concurrent Task Slots can be calculated with the below formula:

$$\text{Total Task Slots } (S) = \text{Total Executors } (E) \times \text{Cores per Executor } (C)$$

For example, if we have 3 executors, each executor has 2 cores, in total we have `6 Total Concurrent Task Slots`.

> It means the cluster can run 6 tasks in parallel.
> 
You can notice the default value is `1 vCore = 1 task`. If your tasks run heavy computational logic 
(e.g., multi-threaded C/C++ libraries, XGBoost, or deep learning inference), you can assign multiple CPU cores 
to a single task slot. This reduces the number of simultaneous task slots per executor to avoid CPU contention.

For example, with the below spark session config, you will have 2 vCore per task

```python
# 6 executor cores / 2 cpus per task = 3 Simultaneous Task Slots per executor
spark = SparkSession.builder \
    .master("yarn") \
    .config("spark.executor.cores", "6") \
    .config("spark.task.cpus", "2") \
    .getOrCreate()
```
> We don't recommend you to chang this value unless you know what you are doing.
>
#### 2.1.3 Aligning task slots with data partition.

If we take the above examples, we have 8 data partitions and 6 task slots. For a data transformation, the cluster needs
two waves to complete all the tasks. The first wave will compute 6 data partitions, the second wave will compute 2 data
partitions.

> You can notice in the second wave, only 2 task slot has been used, the other 4 are idle. The speed of calculation will 
> be the same for 2 executors. So we wast our resource for nothing.
> 
The golden rule is:

For Data Partition Count (P) and Total Task Slots(S): $$P \pmod S = 0$$


### 2.2 Memory management of a spark job

#### 2.2.1 Spark driver memory

Normally, the spark driver only requires `lightweight memory for DAG generation and task coordination`, 
but requires massive memory under two conditions:
- `Broadcast Joins`: The driver builds the broadcast hash table in its own local memory first. Set Driver Memory to 
             at least two times of the Size of Largest Broadcast Table. 
- `Data Collection`: Calling function such as `.collect()` forces executors to send all partitions to the Driver JVM.
              To avoid driver OOM, set a value of `spark.driver.maxResultSize` to prevent full cluster crashes.


#### 2.2.2 Spark executor memory

The memory in spark executor has two main roles:
- data caching (all spark operations works on memory)
- rdd shuffle operations, broadcasting, etc.

The basic rules if `for one core reserve 4-8GB memory`, based on your spark operation. If there are many shuffle operations
increase memory to 8GB for one core.

Key Optimization RulesBalance Heap vs. Off-Heap Memory:Total memory requested from YARN or Kubernetes per executor is:$$\text{Total Memory} = \text{spark.executor.memory} + \text{spark.executor.memoryOverhead}$$Rule: Set memoryOverhead to 10%–15% of executor memory (minimum 384MB). Increase this overhead to 20%–30% if running PySpark or using heavy vectorized operations (PyArrow/Pandas/Polars).Tune Execution vs. Storage Fraction: By default, 60% of usable executor heap (spark.memory.fraction = 0.6) is split dynamically between Execution (shuffles/joins) and Storage (cached DataFrames).Heavy ETL/Transforms: If your job does massive joins but no .cache(), lower spark.memory.storageFraction (e.g., 0.2) so execution memory has priority and won't spill data to disk.Heavy Caching / Iterative ML: If re-using cached tables, keep storage fraction higher so cached partitions aren't evicted.

### 2.3 Core-to-Memory Ratio Efficiency (OS & YARN Allocation)

For Standard spark jobs, we usually maintains a core-to-RAM ratio of roughly `1 core to 4GB–8GB of RAM`.

For example If you have an executor with 5 cores:
- You should pair it with around 16GB to 20GB of executor memory + 2GB memory overhead.
- Total executor size $\approx 5\text{ vCores}, 22\text{GB RAM}$.
- On a standard worker node (e.g., 16 vCores, 64GB RAM), you can fit 3 executors cleanly per node, 
    leaving 1 core and ~12GB of RAM for the OS, YARN NodeManager, and the HDFS DataNode daemon.

## 3. Best practices

There are many best practices when defining a spark executor:
1. `Avoid fat executor`: Assign 4 to 5 cores per executor to maximize throughput while avoiding I/O thread bottlenecks.
2. `Avoid tiny executor`: Running 1-core executors strips away the benefits of shared memory within a JVM process. 
                        Broadcast variables, metadata, and cached datasets must be duplicated across every single 
                         executor process on the node, bloating memory consumption.
3. `Use light driver`: Normally, your spark driver does not require many vCores, 4 vCores can handle 100-500 executor. But 
               if your job use other library which is not spark(e.g. pandas with pyspark, or dplyr with sparklyr), 
               you need to add more vCores and memory, because all these calculation will be on spark driver. 


## 4. Config example

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("OptimizedYARNClusterApp") \
    .master("yarn") \
    .config("spark.submit.deployMode", "client") \
    \
    # Dynamic Allocation (Let YARN manage executors)
    .config("spark.dynamicAllocation.enabled", "true") \
    .config("spark.dynamicAllocation.minExecutors", "1") \
    .config("spark.dynamicAllocation.maxExecutors", "12") \
    .config("spark.dynamicAllocation.executorIdleTimeout", "60s") \
    .config("spark.shuffle.service.enabled", "true") \
    \
    # Sizing per Executor (Tailored for YARN containers)
    .config("spark.executor.cores", "4") \
    .config("spark.executor.memory", "16g") \
    .config("spark.executor.memoryOverhead", "2g") \
    .config("spark.driver.memory", "4g") \
    \
    # SQL & Performance Settings
    .config("spark.sql.adaptive.enabled", "true") \
    .config("spark.sql.adaptive.coalescePartitions.enabled", "true") \
    .config("spark.serializer", "org.apache.spark.serializer.KryoSerializer") \
    .getOrCreate()
```
